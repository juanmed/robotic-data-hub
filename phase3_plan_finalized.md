# Phase 3 Payment Plan

## Summary
- Phase 3 implements a hosted, webhook-driven payment flow with Stripe as the default provider behind a narrow payment-gateway abstraction.
- The backend is the source of truth for pricing, payment status, entitlements, and refunds/disputes.
- The frontend only initiates checkout, shows state, and polls for completion; it does not finalize payment or store card data.

## Implementation Changes
- Define the payment state machine before coding:
  - `order_payment_status`: `pending -> processing -> succeeded | failed | canceled | refunded | disputed`
  - `entitlement_status`: `active | revoked`
  - Explicit transition rules so payment state and access state are not conflated.
- Split data ownership:
  - Keep `orders` for payment records and provider reconciliation metadata.
  - Add a separate `entitlements` table for access control, linked to `buyer_id`, `listing_id`, and `source_order_id`.
  - Store `granted_at`, `revoked_at`, `revoke_reason`, provider IDs, and idempotency metadata.
- Add backend functions for:
  - checkout-session creation
  - webhook verification and processing
  - billing-portal session creation
  - access reconciliation / status lookup
- Make checkout creation server-owned:
  - frontend sends `listingId` only
  - backend calculates the authoritative amount from the listing
  - backend rejects stale or mismatched client pricing
- Use a single purchase entrypoint that branches server-side:
  - free listings create a completed order plus entitlement immediately
  - paid listings create a hosted checkout session
- Add concurrency control:
  - enforce a unique active checkout per buyer/listing
  - use DB constraints plus a server-side lock or transactional upsert so duplicate clicks do not create duplicate charges or entitlements
  - persist and reuse the same idempotency key across retries until the checkout attempt reaches a terminal state or expires
- Make webhook confirmation the source of truth:
  - return URLs are UX only
  - if the user closes the browser before the webhook arrives, the success page shows “processing” and polls the backend until the webhook confirms the order
  - add a scheduled retry / cleanup path for stale pending or orphaned checkouts
- Add a reconciliation path that is explicit:
  - webhook is primary
  - on access-requiring actions, the backend checks for stale payment state and can query the provider API before issuing access
  - do not rely on an ad-hoc, undefined job
- Handle refunds and disputes explicitly:
  - phase 3 detects provider-initiated refund/dispute webhooks and revokes entitlements
  - in-app refund initiation is out of scope for phase 3; refunds are handled in the provider dashboard
- Update the UI:
  - `ListingPage` and `CheckoutModal` show initiating / processing / success / error states
  - add a dedicated success/cancel return route
  - show a retry or refresh path if webhook confirmation is still pending
  - keep the current listing UX intact for free vs paid branching
- Replace the `SettingsPage` payment tab placeholder with a minimal hosted billing portal entry point:
  - view recent orders / receipts
  - update payment method
  - no custom billing dashboard in phase 3
- Add safe audit logging:
  - checkout initiated
  - webhook received
  - payment succeeded / failed / canceled
  - entitlement granted / revoked
  - reconciliation triggered
  - avoid logging secrets or raw webhook payloads

## Test Plan
- Unit tests:
  - payment state machine transitions
  - amount validation and backend quote generation
  - idempotency key generation and reuse behavior
  - provider abstraction methods
  - success-page polling behavior
- Backend tests:
  - checkout-session creation
  - webhook signature verification
  - duplicate webhook handling
  - duplicate checkout click handling
  - stale session reconciliation
  - refund/dispute revocation
  - access checks for entitlements
- Integration tests:
  - free listing purchase path
  - paid listing purchase happy path
  - cancel return path
  - failed payment path
  - webhook-confirmed success path
  - browser-closed-before-webhook path
  - post-payment download/access path
  - refund/dispute access loss path
- RLS tests:
  - buyer can read own orders and entitlements
  - seller can read orders/entitlements tied to their listings
  - service-role writes are allowed for webhook processing
  - unauthorized reads and writes are denied
- UI tests:
  - pending / processing / success / error states in checkout
  - payment portal entry flow in settings
  - free vs paid branching behavior
  - duplicate-click prevention on checkout launch

## Assumptions
- Stripe is the only provider in phase 3, but the code should stay behind a minimal abstraction so a second provider is not baked into the UI.
- Phase 3 is USD-only; tax handling is out of scope unless Stripe automatic tax is turned on intentionally.
- The payment portal is minimal and hosted; it is not a custom billing management area.
- Download URLs are short-lived, and revocation affects future access requests rather than interrupting an already-started transfer.
- The frontend never sends the final amount; it only requests a checkout for a listing.
- The backend’s webhook processing is authoritative, and success/cancel return pages only reflect status.
- The phase order is:
  - state machine and entitlement model
  - schema and constraints
  - backend payment functions and reconciliation
  - frontend checkout wiring
  - settings/billing portal UI
  - tests and hardening
